Issues & fixes

An issue is one agent on one host that was not healthy at pre-check (missing, inactive, failed, not reporting, unhealthy). It counts as fixed only when post-validation after remediation shows it healthy.

BLOCKED_BY_POLICY means the platform deliberately did not run (or could not run) Ansible for that host: missing install payloads on the orchestrator (Sentinel AMA, Arc installer), sudo not available for the SSH user, Falcon/Tanium wrong OS build (manual reinstall with maintenance token), or no catalog action for that agent state. REMEDIATION_FAILED means Ansible ran but post-check still shows a problem (playbook error, Arc connect failure, or agent still unhealthy — e.g. CrowdStrike AID not registered yet). Hover the Details column in the fleet table for the exact reason.

System architecture

Everything runs on one orchestrator host. Inputs arrive on the left, the eight internal layers run top to bottom, and the only outbound traffic to the fleet is SSH on port 22 (read-only health collection, then Ansible remediation when DRY_RUN=false).

Full pipeline: fetch / drop → completion

One picture of the whole run, colour-coded by phase: intake, trigger, validate, state & fleet engine, SSH, health, decide, remediate, post-validate and finalize & outputs. Stores sit on the left; dashed arrows to the right are where a host or run stops, with the status it ends in. Steps 7–11 repeat for every machine, 10 at a time.

End-to-end run flow

  1. TriggerCron (monthly_controller.py) or manual initiate_run.py --dry-run | --production
  2. Locate reportreports/drop/linux_servers_full_agent_status.csv|xlsx, or Graph email fetch when o365_email is enabled
  3. Snapshot & validateCopy to reports/incoming/ + archive, SHA-256, freshness check; invalid → execution closed as invalid
  4. Parse & upsertColumn mapping, IPv4 extraction, de-dup; servers upserted; execution row created as running
  5. Inventoryautomation/inventories/EXEC-*.yml written for Ansible
  6. Load credentialsRegistry synced from credentials.json; passwords resolved in memory only
  7. Fleet loopEach host goes through the per-host decision flow below, in parallel batches
  8. FinalizeCounts aggregated, status completed / dry_run_completed / safety_paused
  9. Excel + notifyreports/generated/EXEC-*.xlsx; JSON summary printed with report_path

SSH credential loop

Each credential set is a fixed username + password pair. For one host the collector walks the sets in order and stops at the first success:

cred-Nuser + password
→
Paramikolegacy KEX, ssh-rsa
→
OpenSSH + sshpassfallback on auth / transport error
→
success?yes → collect · no → cred-N+1
Outcome of an attemptWhat happens next
AuthenticatedStop; this set becomes the host's credential for collection and Ansible.
Password rejectedWait 0.3 s, try the next set.
Banner error / connection resetRetry the same set once after 2 s (handles sshd MaxStartups throttling).
Host key changedssh-keygen -R on secrets/known_hosts, retry once.
No route / refused / timed outHost-level failure: skip remaining sets → SSH_FAILED.
New host keys are recorded with ssh-keyscan under a lock, so parallel workers cannot corrupt known_hosts. Repeated wrong passwords can trigger pam_faillock on targets; adding a credential_hint column to the CSV makes the right set go first.

REMEDIATION_FAILEDAnsible ran but post-check not healthy

Per-agent values in the compliance sheet: HEALTHY, MISSING, INACTIVE, FAILED, NOT_REPORTING, UNHEALTHY, UNKNOWN.

Execution model

  • All hosts are attempted. The safety pause counts remediation failures only (FLEET_PAUSE_ON_SSH_FAILURES=false).
  • Ansible uses only the credential set that authenticated on that host.
  • DRY_RUN=true by default; --production is required for live changes.
  • No general shell endpoint: remote commands are limited to the collector script and catalog playbooks.

One-time setup

cd Self_healing && python3 scripts/verify_readiness.py

Dry-run

python3 scripts/initiate_run.py --dry-run --force-rerun --parallel 15

Production

nohup python3 -u scripts/initiate_run.py --production --force-rerun --allow-stale-report --parallel 10 > logs/fleet-prod-$(date +%F).log 2>&1 &
--production forces live mode for the run regardless of DRY_RUN in .env; the log prints PRODUCTION: live remediation enabled and the execution row has dry_run=0. Keep --parallel ≤ 10. Re-running the same command while an execution is still running resumes it and skips hosts already recorded. --allow-stale-report bypasses the 36 h report-age guard.
